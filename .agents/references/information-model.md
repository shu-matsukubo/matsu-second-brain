# knowledgeの情報モデル

## 配置

knowledgeは情報の性質を表す大分類、その中のテーマ、1主題のファイルという順で配置する。

```text
knowledge/<大分類>/<テーマ>/<主題>.md
```

| 大分類 | `type` | 保存する情報 |
| --- | --- | --- |
| `01-facts` | `fact` | 外部世界や現在の設定について確認可能な事実 |
| `02-principles` | `principle` | ユーザー自身の判断基準、価値観、設計原則 |
| `03-ideas` | `idea` | 未確定の案、試したいこと、可能性、将来構想 |

大分類の中はテーマで分ける。既存のテーマを優先し、別名や細かすぎるテーマを増やさない。複数テーマに関係する場合は主題を最も自然に探せる1テーマへ置き、他テーマからはリンクで辿れるようにする。

## 分類の判断

### fact

- 信頼できる一次情報、実際の設定、再現可能な観測などから確認できる。
- 推測、予測、未検証の説明をfactとして保存しない。
- 外部仕様は可能な限り一次情報への標準Markdownリンクと確認日を本文に残す。
- ローカル設定は確認したファイルや実行結果を根拠にし、将来変わり得る現在値であることが分かるようにする。

### principle

- ユーザーが判断基準や原則として明示している場合は作成できる。
- 明示されていない場合は、複数の独立した観測から一貫した判断傾向を確認できる場合に限る。
- 一度の弱い発言、その時点だけの好み、AIの一般化だけを根拠にしない。それらは必要に応じてsignalsへ置く。

### idea

- 未確定であることを本文で明確にし、事実や決定事項のように断定しない。
- 評価に必要なfactをまず既存の `01-facts` から探してリンクする。現在の配置へまだ整えられていないknowledgeにも同じ事実がないか検索し、内容からfactと確認できる既存ファイルがあれば重複作成しない。
- 必要なfactがなく、信頼できる情報源から確認でき、ideaの理解に有用な場合だけ、必要最小限のfactを別ファイルとして作成する。
- factを作る必要がない場合や検証できない場合は、無理に増やさない。大量の事実説明をidea本文へ埋め込まない。

1つの入力に事実、原則、案が混在するときは、独立して参照する価値がある単位へ分ける。分類に迷うこと自体を理由に、複数の性質を1ファイルへ混在させない。

## ファイルの責務

- 1ファイル1主題とする。
- 別々に参照できる概念は分割する。
- 追記で巨大化させるより、小さな新規ファイルと関連リンクを選ぶ。
- dailyの文章をそのまま複製せず、knowledge単体で理解できるように整理する。
- dailyを参照元としてknowledgeからリンクしない。入力履歴はdailyに残る。

## メタデータ

現在の設計で作成または整備するknowledgeは、次のfrontmatterを基本とする。

```yaml
---
title: 主題
type: fact
topic: テーマ
tags:
  - 必要な検索語
updated: YYYY-MM-DD
---
```

`type` は `fact`、`principle`、`idea` のいずれかとし、配置先の大分類と一致させる。`topic` はテーマフォルダ名と一致させる。`tags` は分類を代用するものではなく、検索に有用な場合だけ付ける。

既存ファイルがこの形式と異なる場合も、通常のメンテナンス対象として1件ずつ整える。内容を確認せず、パスや既存メタデータだけからtypeを機械的に決めない。
