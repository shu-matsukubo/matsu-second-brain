# signalsの運用

## 責務

signalsは、単体ではknowledgeにする根拠や長期価値が足りないが、繰り返し現れた場合に意味を持つ観測を一時的に保つ場所である。dailyをsignalsの保管庫として兼用しない。

次のような情報を対象にする。

- 一時的な感想や好みのうち、今後の判断傾向につながる可能性があるもの
- まだ意味が見えていない短い断片
- 一度だけ現れた弱い判断傾向
- 雑談の中に現れた、再観測すると価値が出る短い発言

長期的な意味を持つ可能性がほぼない雑談や、その場限りの連絡まで保存しない。未検証の外部情報をsignalsへ移して、factの検証を回避しない。

## 保存形式

```text
signals/YYYY/MM.md
```

テーマ見出しの下へ、1つの観測を1つの短い箇条書きで記録する。反復時期を判断できるよう、dailyの作成日など実際の観測日を付け、その年月のファイルへ保存する。

```markdown
## Neovim

- 2026-08-23: フロント開発では少し扱いづらいと感じた

## AIツール

- 2026-08-23: 管理対象が増えること自体をコストと感じた
```

daily本文や長い説明を複製しない。同じdailyから同じ意味のsignalを重複追加しない。

## 週次レビューでの評価

- 直近のsignalsと、まだknowledgeへ反映されていないsignalsを確認する。
- 複数の独立したsignalから一貫したパターンが確認できる場合だけ、principleなどへの昇格候補として週次レポートへ記載する。
- 候補には根拠となるsignalのファイルと観測内容を示す。
- 既存knowledgeですでに表現されている場合は、新規knowledgeではなく、重複するsignalの整理候補とする。
- 週次レビューはsignalsを変更しない。

## 日次メンテナンスでの反映

未処理dailyがないとき、最新の週次レポートに未解消の昇格候補があれば1件だけ処理する。

1. 根拠となるsignalsと既存knowledgeを再確認する。
2. 現在も十分な根拠があり、既存knowledgeと重複しないことを確認する。
3. 適切なtypeとtopicの小さなknowledgeを作成または更新する。
4. 関連リンクとIndexを更新する。
5. 意味がknowledgeへ十分反映されたsignalの箇条書きを削除する。独立した未反映の意味が残るsignalは残す。
6. 空になったテーマ見出しや月次ファイルは残さない。

反映済みsignalを削除することで、同じ観測が毎週同じ昇格候補にならないようにする。元の入力履歴がdailyに残るため、追加の履歴管理は作らない。
