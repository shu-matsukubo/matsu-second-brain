# 第二の脳を日次レビューする

## 原則

- 第二の脳全体を俯瞰して評価する。
- 日次レポートと `.state/daily-review.txt` だけを作成または更新し、`knowledge`、`indexes`、`signals`、`daily`、`feedback` を変更しない。
- 根拠のない推測を記載しない。
- 改善を強制せず、事実と観測を分けて記載する。
- 過去の形式を固定基準にせず、現在の `AGENTS.md` を評価基準にする。
- `reports/weekly` は歴史的記録として保持し、日次形式へ書き換えない。

## referenceの選び方

`AGENTS.md` で全体の現在の思想と正しい状態を確認した後、この `SKILL.md` から必要なreferenceを直接読む。curate Skillや日次の変更手順は読まない。

- 全体の調査観点は、[評価観点](references/inspect-knowledge-base.md)を読む。
- レポートを書き始める段階で、[日次レポート形式](references/write-daily-report.md)を読む。

## 定期起動のstate判定

定期起動またはレビュー周期を指定しない依頼では、調査を始める前に `AGENTS.md` の共通state原則を適用する。

1. `knowledge` と `indexes` のコミット済みGit tree SHAを取得する。
2. `HEAD` の `.state/daily-review.txt` を読み、2つの監視値と作業ツリーの状態を照合する。
3. 有効なidle stateと現在値が一致する場合は、調査、レポート変更、state更新、commitを行わず終了する。
4. stateがactiveまたは無効なら、SHAが前回実行から変わっていなくても全評価を行う。監視対象に未コミットまたは未追跡の変更がある場合は収束済みにしない。

ユーザーが再レビューを明示した場合はidle stateでも評価を行ってよいが、収束stateの更新には同じ収束条件を適用する。

## サブエージェントによる調査

調査範囲が複数の独立した観点へ分かれ、委譲によって速度または品質が上がる場合は、次のカスタムサブエージェントへ必要な調査だけを委譲できる。

- [`knowledge_semantics_reviewer`](../../../.codex/agents/knowledge_semantics_reviewer.toml): knowledgeの意味品質・分類とsignalsの反復・昇格可能性
- [`reference_integrity_auditor`](../../../.codex/agents/reference_integrity_auditor.toml): IndexとMarkdown linksの参照整合性
- [`activity_evidence_reviewer`](../../../.codex/agents/activity_evidence_reviewer.toml): daily、Git履歴、前回レビュー、feedbackの活動証跡

毎回すべてを起動せず、親がレビューの広さ、変更量、調査間の依存関係から委譲先を選ぶ。独立して実行できる調査は並列化してよい。委譲時は対象期間、基準となる前回レポートまたはコミット、担当範囲を明示し、根拠となるパス・件数・確認できない点を返すよう依頼する。

サブエージェントの結果は観測材料であり、改善候補・昇格候補の採否と優先度は親が現在のファイルと照合して決める。親はレポートの作成、変更範囲の確認、commitを委譲しない。

## 手順

1. `AGENTS.md` を読み、現在の全体基準を確認する。
2. [評価観点](references/inspect-knowledge-base.md)を読み、必要な調査範囲と相互依存を確認する。
3. 必要に応じて該当するカスタムサブエージェントへ調査を委譲し、独立した調査は並列化する。委譲しない観点は親が直接確認する。
4. 評価観点の全項目が親またはサブエージェントの調査で覆われていることを確認し、結果の重複、矛盾、未確認事項を現在のファイルと照合する。
5. 親が既存データと現在の基準との差、未解消のfeedback、signalsの反復、前回候補とGit履歴を統合し、通常の日次メンテナンスで扱える改善候補と、根拠が十分な昇格候補を判断する。日次レビュー自身は改善や昇格を実行しない。
6. レポートを書き始める段階で日次レポート形式を読み、現在日の `reports/daily/YYYY/MM-dd.md` を新規作成する。同日のファイルがあれば現在の状態を再評価し、内容が変わる場合だけ更新する。
7. 改善候補、昇格候補、現在の設計との差、次の処理へ渡す価値があるその他の特筆事項がすべてない場合は、レポートへ「特筆事項なし」と明記する。監視対象がクリーンであることも再確認できた場合だけ、現在SHAと `status=idle` を `.state/daily-review.txt` へ書く。
8. 候補または特筆事項が1つでも残る場合、確認不能な場合、監視対象がクリーンでない場合はstateを進めない。同じSHAでも次の日次起動で再評価できるactive状態を維持する。
9. 日次レポート、および収束した場合の専用state以外にファイルが変更されていないことを確認する。内容が変わらなければ不要なcommitを作らず、変更があれば対象ファイルだけをcommitする。処理またはcommitに失敗した場合は前回コミット済みstateを進めない。
10. 保存先、主な観測、日次メンテナンスへ渡した候補、収束判定を簡潔に報告する。
