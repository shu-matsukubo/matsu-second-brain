# 第二の脳を整理する

## 原則

- `AGENTS.md` を第二の脳全体の現在の基準とする。
- 定期reconcilerの共通state原則は `AGENTS.md` に従い、処理途中や対象が残る状態で収束済みにしない。
- 1回の実行では、主対象を1つに限定する。
- 変更を小さく保ち、レビューしやすい状態を維持する。
- ユーザーが処理方法を指定した場合は、その指定を優先する。
- 対象がない場合や有益な変更が見つからない場合は、変更せず終了する。
- 推測でナレッジを作成または更新しない。
- 主対象の完了に必要な関連fact、リンク、Index、dailyのstatus、signalsの変更は同じ作業に含めてよい。

## referenceの選び方

処理方法はこの `SKILL.md` から直接、必要なreferenceだけを選ぶ。referenceから別のreferenceを順番に辿ることを通常経路にしない。

- dailyを整理するときは、[daily整理](references/ingest-daily.md)を読む。
- 日次レポートの候補または既存データを整えるときは、[メンテナンス](references/maintain-knowledge.md)を読む。
- knowledgeの作成、移動、改名、分類変更に伴ってIndexまたはリンクを変えるときだけ、[Indexとリンクの更新](references/update-indexes-and-links.md)を読む。
- dailyからsignalを保存するとき、または日次レビューの昇格候補を反映するときだけ、[signalsの記録と反映](references/manage-signals.md)を読む。

## 定期起動のstate判定

ユーザーが特定の処理を明示していない定期起動では、処理対象を探す前に `AGENTS.md` の共通state原則を適用する。

1. `daily`、`knowledge`、`reports/daily` のコミット済みGit tree SHAを取得する。`reports/daily` がまだなければ `daily_reports=missing` とする。
2. `HEAD` の `.state/curate-second-brain.txt` を読み、監視値と作業ツリーの状態を照合する。
3. 有効なidle stateと現在値が一致する場合は、対象探索、ファイル変更、state更新、commitを行わず終了する。
4. それ以外はactiveとして通常処理へ進む。監視対象に未コミットまたは未追跡の変更がある場合は、処理できる範囲を安全に扱ってよいが、この実行では収束済みにしない。

ユーザーが対象や処理方法を明示した場合は、その依頼をstateによる早期終了より優先する。ただし、その実行だけを根拠にワークスペース全体を収束済みにはしない。

## 処理を選択する

1. dailyの処理を明示された場合は、daily整理を選択する。
2. メンテナンスを明示された場合は、メンテナンスを選択する。
3. 処理方法が指定されていない場合は、`daily` 内から `status: new` のメモを探す。複数ある場合はfrontmatterの作成日時、取得できなければパス上の日付が古いものを1件選ぶ。statusが欠けている、または解釈できないファイルを推測で未処理または処理済みにしない。
4. 未処理dailyが見つかった場合は、最も古い1件のdaily整理を選択する。
5. 未処理dailyがない場合だけ、`reports/daily` の最新レポートにある未解消の改善候補または昇格候補を確認する。
6. 有益な日次候補があれば1件をメンテナンスし、なければ現在の設計との差を1件メンテナンスする。
7. 1回の実行でdaily整理とメンテナンスの両方を行わない。

## dailyを整理する

referenceの選び方に従ってdaily整理を読み、入力全体をknowledge、signals、保存不要な一時情報へ安全に振り分ける。未検証の事実主張をfactへ入れない。

## メンテナンスする

referenceの選び方に従ってメンテナンスを読み、最新の日次候補または現在の設計との差から主対象を1件選ぶ。日次レポートの観測を鵜呑みにせず、現在も未解消か確認してから変更する。

## 終了と収束を確定する

- 主対象の完了条件を満たし、Index、リンク、status、signalsに不整合がないことを確認する。
- 変更が1つの意味的な作業に収まり、無関係な既存変更を含んでいないことを確認する。
- 作業中に得た事実や気付きは、必要な場合だけ `AGENTS.md` のフィードバック方針に従って記録する。
- 主対象を処理した場合は、この処理で変更したファイルだけをまとめてコミットし、既存の無関係な変更を含めない。内容を変更した実行では `.state/curate-second-brain.txt` を収束済みへ進めない。
- 定期起動で主対象が見つからなかった場合だけ、未処理dailyがなく、最新の日次レポートと現在の設計を確認しても有益なメンテナンス対象がなく、監視対象がクリーンであることを再確認する。すべて満たす場合は現在の3つの監視値と `status=idle` をstateへ書き、stateだけをcommitする。
- 対象が残る、確認不能、処理やcommitに失敗した場合はstateを進めない。stateファイル自体は削除しない。
- 実施内容、対象、変更しなかった理由がある場合はその理由を簡潔に報告する。
