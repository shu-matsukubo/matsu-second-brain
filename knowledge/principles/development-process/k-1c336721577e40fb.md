      # AIフローでは能力・制御・判断知識を分離する\r

      \r

      AIエージェント基盤では、個別の能力、工程の制御、複数工程で使う判断知識の責務を分ける。\r

      \r

      - Skillは単一の能力を提供する。\r

      - Workflowは複数のSkillを使って工程を制御する。\r

      - Referenceは複数工程から利用する判断知識を持つ。\r

      - `AGENTS.md` は安定した原理原則を持つ。\r

      \r

      Skill自身に他のSkillや工程の前後関係を持たせず、フローを変更したときに能力側まで連鎖して修正されない構造を選ぶ。\r

      \r

      再利用するSkillは、その能力とWorkflowの範囲で自己完結させる。Agent全体の基本方針、特定モデル向けの設定、リポジトリ全体のルール、\
      他のSkillを前提とする設定はホスト環境に置く。Skillを導入しても、利用側Agentのグローバルな振る舞いまで変えない。\r

      \r

      汎用WorkflowのCoreには成果物生成で守る原理原則を置き、成果物固有の生成手順はExtensionへ委譲する。対応するExtensionが\
      ない場合はCoreだけで実行する。Reviewでは独立した観点のExtensionを組み合わせられるが、Generationでは手順の競合を避ける\
      ため用途に合うものを1つ選ぶ。\r

      ```text
## Workflowの状態は既存成果物から導出する

Workflowの進捗管理だけを目的に、
新しいラベルやステータスを増やさない。

まず、

- PR
- Branch
- Commit
- 作業記録

など、処理の結果として自然に存在する事実から
現在状態を導出できないか考える。

例えば、

Open PRが存在する
→ 実装済み・レビュー待ち

と判断できるなら、
「レビュー待ち」ラベルを別途管理しない。

同じ状態を複数箇所へ保存すると、
それらの同期と不整合処理が新しい責務になる。

状態を保存する前に、
既存の事実から計算できないか確認する。

また、定期実行などの上位Workflowは
既存の実装・レビュー手順を再実装せず、
処理順と停止条件だけを持つ薄い
Orchestration Layerとして設計する。
```
