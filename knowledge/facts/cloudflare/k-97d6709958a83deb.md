# 内容

Cloudflare Workersの初回公開では、プロジェクトの依存・設定、認証先、対象環境、シークレットを確認して公開方法を選ぶ。ここでは、Wrangler設定を持つ既存プロジェクトからの通常の公開を扱う。特定アプリのビルド方法や公開先がこの手順で確認済みという意味ではない。

## 依存と認証

Node.jsとnpmを用意し、プロジェクトで定めた方法で依存を復元する。Wranglerはローカル依存の版を使う。未導入のまま `npx wrangler` を呼ぶと最新版が使われるため、利用する版を確認する。

対話環境では、必要に応じてOAuthログインを行う。

```shell
npx wrangler login
```

非対話のCIでは `CLOUDFLARE_API_TOKEN` と `CLOUDFLARE_ACCOUNT_ID` をCI側で設定する。APIトークンの対象アカウント・権限を必要な範囲に絞り、リポジトリへ値を書かない。

## 環境とシークレット

Worker名、アカウント、ルート、必要なバインディングを対象設定で確認する。通常のWrangler環境では `--env production` のように指定し、シークレット操作も同じ対象へ合わせる。環境ごとのシークレットは継承されない。

`wrangler secret put` は値の準備だけを行う操作ではなく、新しいWorkerバージョンを作り直ちにデプロイする。旧本文の「シークレットを事前登録してからdeployする」という一律の順序は、各操作の影響を確認して選ぶ必要がある。

コードとシークレットを同時に送る場合、対応するWranglerでは `deploy --secrets-file` にJSONまたは.env形式のファイルを渡せる。ファイルは安全に管理し、Gitへ含めない。初回Worker作成前に `secret put` を必ず先行できるという前提を置かず、必要な値と公開方法を揃える。詳細は関連するシークレットノートを参照する。

## 公開コマンドの例

設定済みプロジェクトでの通常の公開は次の形になる。以下は説明用の例であり、今回実行したコマンドではない。

```shell
npx wrangler deploy --env production
```

コードとシークレットを同時に送る構成の例は次のとおり。ファイルの場所は管理方法に合わせて指定する。

```shell
npx wrangler deploy --env production --secrets-file /secure/path/worker-secrets.json
```

`npm run deploy` はプロジェクト側が定義するscriptを実行する。Wranglerに渡す引数やビルド処理が一致するとは限らないため、`package.json` の内容を確認する。Cloudflare Vite pluginを使う構成では、環境をdev/build時の `CLOUDFLARE_ENV` で選ぶなど手順が異なるため、通常の `--env` の例をそのまま適用しない。
