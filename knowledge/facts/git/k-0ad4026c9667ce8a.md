      # Git の作業領域とリモートの全体像\r

      \r

      Git の基本的な流れは、作業ツリーで変更し、インデックスに次のコミットの内容を準備し、ローカルリポジトリにコミットとして記録した後、必要に応じてリモートリポジトリと履歴をやり取りする、というものになる。\r

      \r

      ```text\r

      作業ツリー\r

      \    │  git add\r

      \    ▼\r

      インデックス（ステージングエリア）\r

      \    │  git commit\r

      \    ▼\r

      ローカルリポジトリ（コミット、ブランチ、リモート追跡ブランチ）\r

      \    │  git push\r

      \    ▼\r

      リモートリポジトリ\r

      \r

      リモートリポジトリ\r

      \    │  git fetch\r

      \    ▼\r

      ローカルのリモート追跡ブランチ\r

      ```\r

      \r

      矢印は、各コマンドが主にどの領域の内容を基に、どの領域を更新するかを示す。`git restore`、`git checkout`、`git reset` などによる逆方向の更新は省略している。また、`git fetch` は現在のローカルブランチや作業ツリーを直接更新しない。\r

      \r

      ## 4つの要素\r

      \r

      ### 作業ツリー\r

      \r

      実際にファイルを開いて編集する場所。通常は現在のコミットの内容に、まだコミットしていないローカルの変更が加わった状態になっている。\r

      \r

      ### インデックス（ステージングエリア）\r

      \r

      次のコミットに含める内容を準備する領域。サーバーや一時環境ではなく、ローカルリポジトリ内で管理されるファイル内容の一覧である。\r

      \r

      - `git add <file>` は、その時点のファイル内容をインデックスへ追加する。\r

      - `git restore --staged <file>` は、通常はインデックスを `HEAD` の状態へ戻し、変更を次のコミット対象から外す。作業ツリーの編集内容は残る。\r

      - `git commit` は、原則としてインデックスに準備された内容を新しいコミットとして記録する。\r

      \r

      コミットの単位を整えるには、ファイル単位または差分のまとまり（hunk）単位でステージする。具体的な選び方と確認手順は [Git でコミットに含める差分を選ぶ](k-ef264754e56ae439.md) に分ける。\r

      \r

      ### ローカルリポジトリ\r

      \r

      コミット、ブランチ、タグなどの履歴をローカルに保持する場所。`git commit` はここに新しいコミットを作る。`git merge` は別の開発履歴を現在のブランチへ統合する操作であり、インデックスからコミットへ移す操作ではない。\r

      \r

      ### リモートリポジトリと remote\r

      \r

      リモートリポジトリは、GitHub など別の場所にあるリポジトリを指す。一方、`origin` や任意に追加した名前は、リモートリポジトリの URL や取得方法をローカルに記録した短縮名であり、「ローカルにあるリモートサーバー」ではない。\r

      \r

      1つのローカルリポジトリには、`origin`、`upstream` など複数の remote を設定できる。名前は任意だが、`origin` は clone 元に自動で付くことが多い慣例的な名前である。\r

      \r

      - `git fetch <remote>` はリモートのオブジェクトを取得し、設定に従って `origin/main` などのリモート追跡ブランチを更新する。ローカルの作業ブランチは自動では更新しない。\r

      - `git push <remote> <branch>` はローカルのコミットと参照を送り、許可されればリモート側のブランチを更新する。\r

      - `git pull` は fetch の後に merge または rebase で現在のブランチへ統合する複合操作である。\r

      \r

      ### fetch と push の向き\r

      \r

      `fetch` と `push` は、ローカルリポジトリを基準に考えると分かりやすい。\r

      \r

      ```text\r

      リモートリポジトリ ── fetch ──▶ ローカルのリモート追跡ブランチ\r

      リモートリポジトリ ◀─ push ─── ローカルブランチ\r

      ```\r

      \r

      引数を省略した `git push` は、常に `git push origin <現在のブランチ>` と同じになるわけではない。送信先は現在のブランチに設定された upstream、`branch.<name>.remote`、`remote.pushDefault` などから選ばれ、送信するブランチは `push.default` などの設定で決まる。既定の `simple` では、通常は現在のブランチを対応する同名の upstream ブランチへ送るが、upstream が未設定の場合などは失敗することがある。\r

      \r

      複数の remote がある場合は、対象を明示すると安全である。\r

      \r

      ```bash\r

      git fetch origin\r

      git push origin main\r

      git push remote2 main\r

      ```\r

# 内容

Git の基本的な流れは、作業ツリーで変更し、インデックスに次のコミットの内容を準備し、ローカルリポジトリにコミットとして記録した後、必要に応じてリモートリポジトリと履歴をやり取りする、というものになる。

```text
作業ツリー
    │  git add
    ▼
インデックス（ステージングエリア）
    │  git commit
    ▼
ローカルリポジトリ（コミット、ブランチ、リモート追跡ブランチ）
    │  git push
    ▼
リモートリポジトリ

リモートリポジトリ
    │  git fetch
    ▼
ローカルのリモート追跡ブランチ
```

矢印は、各コマンドが主にどの領域の内容を基に、どの領域を更新するかを示す。`git restore`、`git checkout`、`git reset` などによる逆方向の更新は省略している。図はリモート追跡参照へ取得する一般的な設定を想定しており、取得先はrefspecなどの設定によって変わる。fetchは取得結果を現在の作業ブランチへ自動統合する操作ではない。

## 4つの要素

### 作業ツリー

実際にファイルを開いて編集する場所。通常は現在のコミットの内容に、まだコミットしていないローカルの変更が加わった状態になっている。

### インデックス（ステージングエリア）

次のコミットに含める内容を準備する領域。サーバーや一時環境ではなく、ローカルリポジトリ内で管理されるファイル内容の一覧である。

- `git add <file>` は、その時点のファイル内容をインデックスへ追加する。
- `git restore --staged <file>` は、通常はインデックスを `HEAD` の状態へ戻し、変更を次のコミット対象から外す。作業ツリーの編集内容は残る。
- `git commit` は、原則としてインデックスに準備された内容を新しいコミットとして記録する。

コミットの単位を整えるには、ファイル単位または差分のまとまり（hunk）単位でステージする。具体的な選び方と確認手順は [Git でコミットに含める差分を選ぶ](k-ef264754e56ae439.md) に分ける。

### ローカルリポジトリ

コミット、ブランチ、タグなどの履歴をローカルに保持する場所。`git commit` はここに新しいコミットを作る。`git merge` は別の開発履歴を現在のブランチへ統合する操作であり、インデックスからコミットへ移す操作ではない。

### リモートリポジトリと remote

リモートリポジトリは、GitHub など別の場所にあるリポジトリを指す。一方、`origin` や任意に追加した名前は、リモートリポジトリの URL や取得方法をローカルに記録した短縮名であり、「ローカルにあるリモートサーバー」ではない。

1つのローカルリポジトリには、`origin`、`upstream` など複数の remote を設定できる。名前は任意だが、`origin` は通常のcloneで取得元に付く既定の名前であり、オプションや設定で変えられる。

`origin/main` はリモート上のmainそのものではなく、その取得結果を追うローカルの参照である。実際のリモートが更新されても、自分の参照が自動で常に最新になるわけではない。

- `git fetch <remote>` はリモートのオブジェクトを取得し、設定に従って `origin/main` などのリモート追跡ブランチを更新する。ローカルの作業ブランチは自動では更新しない。
- `git push <remote> <branch>` はローカルのコミットと参照を送り、許可されればリモート側のブランチを更新する。
- `git pull` はfetchで取得した後、選択された方法で現在のブランチへ統合する。`--ff-only`、`--rebase`、`--no-rebase`、`--squash`や関連設定によって動作が変わる。2026-11-17に確認したWeb版資料では、別の方法を指定しない場合はfast-forwardのみを許し、履歴が分岐していれば失敗する。利用するGit版と設定を確認し、無条件にマージコミットを作る操作とは扱わない。

### fetch と push の向き

`fetch` と `push` は、ローカルリポジトリを基準に考えると分かりやすい。

```text
リモートリポジトリ ── fetch ──▶ ローカルのリモート追跡ブランチ
リモートリポジトリ ◀─ push ─── ローカルブランチ
```

引数を省略した `git push` の送信先と、送る参照は別々に決まる。送信先には`branch.<name>.remote`、`remote.pushDefault`、`branch.<name>.pushRemote`などが関係し、`pushRemote`は他の二つを上書きする。送る参照はコマンド引数や`remote.<name>.push`で指定でき、それらがなければ`push.default`で決まる。

既定の`simple`は送信先の同名ブランチを対象とし、通常取得するremoteへ送り返す場合には同名のupstreamも必要となる。upstreamや自動設定の有無、取得先と送信先の違いによって結果は変わるため、引数なしのpushを常に`git push origin <現在のブランチ>`と同じとは考えない。

複数の remote がある場合は、対象を明示すると安全である。

```bash
git fetch origin
git push origin main
git push remote2 main
```

## 状態を確認するコマンド

```bash
git status
git diff
git diff --staged
git log --oneline --graph --all
git remote -v
git branch -vv
```

- `git status` は作業ツリーとインデックスの状態を要約する。
- `git diff` は主に作業ツリーとインデックスの差分を表示する。
- `git diff --staged` はインデックスと `HEAD` の差分、つまり次のコミット候補を表示する。
- `git log --oneline --graph --all` は、ローカルにある参照（ブランチやタグなど）とHEADから辿れる履歴を短い形式のグラフで表示する。
- `git remote -v` は remote 名と接続先 URL を表示する。
- `git branch -vv` は、ローカルブランチとupstreamの対応、先行・遅延の状態を表示する。リモート追跡参照との比較では、最後に取得したローカルの情報が基準となる。
