# Notionを知識候補の受け皿にする案

これは調査結果と未採用の設計案である。本文はAIによる整理であり、ユーザーが採用した運用方針や支持・反対の根拠として扱わない。`completed`は今回の調査の終了を表し、Notion接続や移行の成功を表さない。

## 結論

公式仕様を組み合わせると、二つの投入元からNotionの同じデータベースへ候補を集め、ローカルの整理処理だけが一件ずつ消費する構成は実現可能性がある。ただし、今回の環境ではNotionの実操作を検証できていないため、採用判断は接続後の小規模試験が条件になる。

推奨する初期案は「Notionに自由記述で投入 → 未処理の一件を確保 → knowledgeとindexを更新 → Notionを完了にする」。完了項目は未処理ビューから隠す。削除は、出典の保全と失敗後再開を確認してから検討する。

## 公式仕様から分かること

| やりたいこと | 判定と制約 |
| --- | --- |
| Codexの定期実行で候補をNotionに投入 | 仕様上の構成候補。デスクトップの定期タスクはプラグインを利用できる。実際にNotionの書き込みツールと権限がその実行環境で使えるかは別途確認が必要 |
| クラウドのチャットの定期実行で投入 | 仕様上の構成候補。Webの定期タスクはそのチャットで利用可能な接続ツール・Skill・プラグインを使える。プランとワークスペース設定に依存する |
| クラウドからこのPCのローカルフォルダを直接整理 | 通常のWeb定期タスクではできない。候補投入をクラウド、Markdown反映をローカルに分ける構成が適する |
| ローカル処理をPC停止中にも実行 | ローカルファイルやローカルSkillを必要とする実行には、PC起動とアプリ稼働が必要 |

以上は[OpenAIの定期タスク仕様](https://learn.chatgpt.com/docs/automations)と[公式の設定例](https://developers.openai.com/training/walkthroughs/scheduled-tasks)による。今回のアカウントでクラウド実行できたことは確認していない。

Notionの公式MCPはページの読み書きとデータベースの作成・プロパティ更新を扱う。ただし、製品が持つ機能すべてがこのチャットのプラグインに公開されるとは限らない。[Notion MCP概要](https://www.notion.com/help/notion-mcp)、[対応ツール](https://developers.notion.com/guides/mcp/mcp-supported-tools)。

REST APIにはデータソースの条件付き取得、並べ替え、ページ送りがある。「未処理の最古一件」を取得する実装に使える。MCP／プラグインで同じ条件取得ができるかは実ツールで検証する必要がある。検索結果だけから全未処理項目を把握したと判断しない。[データソース照会API](https://developers.notion.com/reference/query-a-data-source)。

全チャットの当日分を自動的に横断収集できることは確認していない。まずは指定したチャットの文脈、または明示した取得元を対象にする。候補がない日は作成しない。

## 推奨構成案

```text
Codexの候補収集 ──┐
                  ├─→ Notion「知識候補」 ─→ ローカル整理（一件） ─→ knowledge / index
クラウドの候補収集 ┘                          └─→ Notionの完了status
```

二つの投入元は候補追加だけを担当し、処理済み判定はローカル整理に集約する。一回の整理で主対象を一つに絞る既存方針を維持する。既存dailyとの併用中は、既存の未完了journalを最優先し、dailyとNotion候補の入力日時に基づく選択などを明示して片方が滞留しないようにする。その後にreport対応と全体評価を行う案とする。

Notionは一ページを一入力単位とし、本文は箇条書きや雑なメモでよい。一入力から複数のknowledgeが必要なら、整理側が主題を分ける。処理中のページへの追記を避け、追加内容は新しい項目にする。

Notion側の項目案は次のとおり。利用者に構造化入力を強制せず、投入側が可能な範囲を補う。

| 項目 | 用途 |
| --- | --- |
| タイトル・本文 | タイトルは自動補完可。本文は自由記述 |
| 状態 | 未処理、処理中、完了、保留、エラー。初期値は未処理 |
| 入力元・元の日時 | Codex／クラウド／手入力の識別と処理順 |
| 原文・出典 | 人間の発言の必要部分、チャット等の参照先、外部事実の一次情報 |
| 入力の由来 | 人間原文、AI候補、混在、不明。AI候補の中の人間発言は明確に分離 |
| 重複判定キー | 同じ出典の同じ入力を二つの投入元が重ねて作ることを防ぐ |
| 反映結果 | 完了日時、knowledgeの安定ID、除外した場合の理由 |

処理の正本となるpage ID、内容digest、操作ID、再開段階はローカルの最小限のstateで管理する案とする。本文・出典の変更と、処理側のstatus更新を区別してdigestを作る。

## 既存実装で必要な変更

現行の[scripts/brain.mjs](../scripts/brain.mjs)は、`daily/`内の安全なパスを人間入力とみなす。NotionのAI候補を無加工でdailyへ複製すると、AI文が人間由来の根拠になり得る。支持・反対を数える既存方針に関わるため、単なる取り込み追加では不十分。

二つの移行案がある。

1. **段階移行**：Notionから一件をローカルdailyへ固定スナップショットとして取り込み、既存journalと反映処理を再利用する。ただし、その前に入力由来の扱いを修正し、AI文・混在・不明を人間の支持として計数しないことが必要。Notionの完了通知待ちを別途再開できるようにする。ローカルdailyは当面残る。
2. **直接取り込み**：CLIにNotion入力の種別・出典・digest・完了通知の再開段階を追加し、dailyを経由せず処理する。daily廃止に近いが、operation plan、根拠検証、journal、保留解除条件まで変更対象になる。

最初の実証は段階移行案が小さく試せる。既存dailyを残したくない場合は直接取り込み案が適する。いずれも未採用であり、今回は実装していない。

AIが収集したという理由だけで全内容を捨てる必要はない。外部事実は一次情報で確認し、人間の意思は原文と出典で確認する。AIによる推測や要約自体は支持・反対に数えない。同じ発言の二重取り込みも二回の支持にしない。

また、現行の保留fingerprintはローカル入力だけを監視する。Notion導入後は、保留中でも新規候補を軽量照会し、内容の追加・変更だけで整理を再開する必要がある。status更新だけで探索を再開しない。

## 完了・失敗・削除の扱い

ローカル更新とNotion更新を一つの原子的な処理にはできない前提で、次の順序を提案する。

1. 一件を選び、page ID・内容digest・操作IDを保存して処理中にする。整理側は単一実行とし、重複起動はローカルロックで防ぐ。Notionのstatusだけを排他制御とみなさない。
2. 出典と入力由来を確認し、knowledge更新計画をjournalで適用する。処理中に本文が変わった場合は自動完了せず、固定した版との食い違いを保留する。
3. knowledge、index、必要な根拠・背景、反映台帳を検証し、完了通知待ちの段階を永続化する。保存対象がなければ除外理由を記録して処理を終える。
4. Notionの完了statusと結果を更新し、再取得で確認する。ここだけ失敗した場合は次回に完了通知だけ再試行し、knowledge更新と支持計数を再実行しない。
5. 初期運用では完了ビューへ移すだけにする。後で削除を採用する場合も、ローカルに必要な根拠と重複防止台帳が残り、未完了操作がないことを確認した後に限る。

元の情報をすべて消すと、NotionのURLとhashだけでは入力の意味や人間の意思を復元できない。削除を選ぶ場合に残す原文・背景の範囲、保存先、保存期間は未決定。既存dailyの削除まで今回の検討依頼から実行許可が出たとは扱わない。

既存のAGENTSとdaily Skillは入力保持・statusのみ変更を前提とし、policyも根拠と背景の追跡を求めている。採用時は、まずAGENTS・SkillにNotion入力の扱いを明示し、policyとの整合を確認する。policyの変更は必要性と具体案をユーザーが判断した場合に限る。

## 接続が使えるようになった後の最小試験

専用の試験用データベースで、次を順に確認する。既存の本番整理スケジュールは成功後に変更する。

1. 通常のCodexチャットから一件作成し、page ID指定で本文を読み戻し、状態を更新できること。
2. 未処理の取得・日時順の選択・ページ送りが使え、古い項目も取りこぼさないこと。検索しかない場合は採用を保留し、REST API接続を別案として評価する。無断で方式を切り替えない。
3. Codexの予約実行とクラウドの予約実行をそれぞれ一回ずつ動かし、同じDBへの到着を読み戻して確認する。対話中だけ書けても無人実行で書けるとは判断しない。
4. 同じ入力の再送、二つの投入元からの重複、AI文、混在した人間発言を用い、重複反映や支持回数の誤計数がないこと。
5. ローカル反映後・Notion完了更新前に意図的に止め、次回は完了通知だけ再開できること。本文の途中編集、接続切れ、対象なしの扱いも確認する。
6. 削除を採用する場合だけ、完了後のゴミ箱移動と復元、台帳による再取り込み防止を追加検証する。完全削除は初期試験の対象にしない。

候補収集プロンプト案：指定したチャットまたは明示した情報源の当日分から、長期保存を検討する価値のある入力だけをNotionの知識候補DBへ追加する。人間の発言とAIの提案を分け、元の日時・出典・重複判定キーを付ける。不足を推測で埋めず、候補がなければ作成しない。既存項目の完了や削除は行わない。

整理プロンプト案：既存journalとNotion完了通知待ちを先に再開する。未処理の入力一件だけを現行policyに従ってknowledgeへ反映し、検証後にNotionを完了にする。AI生成文を人間の支持として数えず、失敗時は同一操作を再開できる状態で終了する。
